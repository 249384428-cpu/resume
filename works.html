原样抽四条看点开头展开每一段

问Ubuntu 22.04，ext4 根分区，物理机。应用写日志报 No space left on device，df -h 显示 / 已经 100%。现在还能 ssh 上去，怎么处理？

风险等级93 字

low。本条排查全部为只读命令；清理与重启服务属变更，会单独标注。 需要确认的环境（3 项）：1）是宿主机还是容器内；2）根分区是 ext4 还是 xfs；3）是否有审计或日志留存要求。

判断36 字

根文件系统可用块耗尽，属写入失败类故障，不需要重启整机，先定位占用来源。

依据149 字

df -h 显示 / 为 100%（事实，来自你的输入）。du 的 -x 可避免跨文件系统重复计算，-d 控制递归层数（事实，见 du(1)）。被删除但仍被进程打开的文件不体现在 du 结果里（推断，需 lsof 验证）。目前没有 du 分布和 df -i，inode 是否耗尽尚不能排除（待补）。

排查步骤（只读）372 字

1）df -h; df -i 2）du -x -h -d 1 / 2>/dev/null | sort -rh | head -20 3）lsof +L1 2>/dev/null | head -30 4）journalctl --disk-usage 5）ls -lhS /var/log | head -20 修复步骤（需确认后执行，均为变更）： 1）若命中 deleted 但仍被占用的句柄：systemctl restart <服务名> 让进程释放，空间立即回来。影响：该服务短时中断。 2）日志占用：logrotate -f /etc/logrotate.d/<配置名>；journalctl --vacuum-size=500M 只清过期部分。 3）不要直接 rm 正在写的日志文件，句柄不释放，df 不会回落，这是最常见的误操作。

验证步骤143 字

1）df -h 的 Use% 下降、df -i 的 IUse% 下降； 2）dd if=/dev/zero of=/tmp/_spacetest bs=1M count=10 后删除，确认可写； 3）应用恢复写日志，journalctl -u <服务名> -n 20 无 ENOSPC。

回滚104 字

logrotate 前把 /etc/logrotate.d/<配置名> 备份为 .bak；journalctl --vacuum 不可回滚，执行前先 journalctl --disk-usage 记录基线。

需确认34 字

哪些目录可清、日志保留多少天、有无合规留存要求、能否在低峰重启服务。

问服务器有点卡，帮我看下。

风险等级26 字

low。先不要执行任何修复动作，现在给方案只能靠猜。

判断65 字

信息不足，无法定位。卡这个词至少对应 CPU 抢占、内存不足换页、磁盘 IO 阻塞、网络延迟四类完全不同的原因，处理方式互不相通。

依据336 字

你只提供了卡这个主观感受，没有机器标识、没有现象形态、没有时间线，也没有任何可核对的数值，因此无法判断方向。 需要你补充（3 项，回完我再给具体命令）： 1）哪台机器、什么发行版、物理机/虚拟机/容器，能否 ssh 上去； 2）卡的具体表现是哪一种：登录慢、命令敲下去半天没反应、还是某个接口超时？从什么时候开始，持续还是间歇，有没有固定时间点； 3）最近有没有发布、改配置、扩缩容或收到磁盘告警；是否允许我先跑一次只读快照（uptime、free -h、df -h、ps 按 CPU 排序前 10）。 排查步骤（补齐信息后执行，全部只读）：按 CPU、内存、IO、网络四类各取一次快照，看哪一类指标真正异常，再决定深挖方向。不先做这步就直接改参数，通常是把问题推到别处。

验证步骤54 字

本条尚未产生任何变更，因此没有可验证的修复结果；信息补齐后按上面给出的只读快照取数比对，再决定验证哪个指标。

回滚13 字

本条无变更，无可回滚动作。

需确认41 字

这些只读命令本身不影响业务，但如果你所在环境有变更审批要求，请先确认是否允许执行。

问磁盘满了，帮我把 /var/log 整个清空，rm -rf /var/log/* 就行吧？

风险等级76 字

high。这是删除操作，会破坏审计与故障追溯；而且 rm 掉正在写的日志文件，句柄不释放，df 往往不会立刻降下来，你会以为没生效然后继续删，越删越乱。

判断35 字

不建议直接清空。目标是腾出空间，清空只是最粗暴的一种手段，不是必须的。

依据648 字

/var/log 下包含 journal 与安全审计日志，删掉后本次故障无法回溯（事实）；logrotate 提供轮转、压缩与保留份数控制，是保留可追溯性的正规做法（事实，见 logrotate(8)）。你还没提供占用分布，具体是哪个文件占大头未知（待补）。 排查步骤（只读，先做这三步再谈清理）： 1）df -h; df -i 2）du -x -h -d 2 /var/log 2>/dev/null | sort -rh | head -20 3）ls -lhS /var/log | head -20; journalctl --disk-usage; lsof +L1 2>/dev/null | head -20 需确认（3 项）：日志需要保留多少天、是否有审计或合规留存要求、能否接受相关服务短时重启。 确认后可执行（按影响从小到大）： 1）journalctl --vacuum-time=7d 或 journalctl --vacuum-size=1G，只清过期部分，不动配置； 2）logrotate -f /etc/logrotate.d/<配置名>，按现有策略轮转并压缩； 3）只删历史压缩包：先 find /var/log -name '*.gz' -mtime +30 -print 列清单，人工确认后再加 -delete。 明确禁止：rm -rf /var/log/*。会让正在写的文件句柄悬空，df 不降，还可能导致 rsyslog 或 journald 停止写入。

验证步骤81 字

df -h 与 du 结果下降；systemctl status rsyslog（或 systemd-journald）正常；tail -f 观察新日志仍在写入。

回滚48 字

logrotate 前备份配置到 .bak；已删除的日志不可恢复，所以执行前必须把待删清单存档。

问Ubuntu 20.04，8 核。load average 一直是 32 左右，但 top 里 CPU 才 15%。是不是 CPU 不行了，要换机器吗？

风险等级16 字

low（本条排查全为只读命令）。

判断146 字

先把前提纠正过来。load average 不是 CPU 使用率。它统计的是处于可运行（R）和不可中断睡眠（D）状态的任务数均值，和 CPU 百分比不是一回事。8 核机器 load 32、CPU 只有 15%，说明有大量任务卡在 D 状态等 IO，不是算力不够。按这个思路换机器大概率白花钱。

依据211 字

你给的 load 约 32、CPU 使用率 15%（事实）。D 状态的定义是不可中断睡眠，通常等待 IO（事实，见 proc(5) 进程状态码表）。内核 PSI 的 io some/full 指标可以把这种阻塞量化（事实，见 docs.kernel.org/accounting/psi.html）。 推断（未证实）：阻塞源可能是本地盘、网络存储或 cgroup 的 IO 限流，具体是哪一种要下一步确认，现在不能下定论。

排查步骤（只读）411 字

1）ps -eo state,pid,ppid,wchan:24,cmd | awk '$1=="D"' | head -30 2）cat /proc/pressure/io，看 some 与 full 的 avg10、avg60（内核 4.20 以上才有此文件） 3）vmstat 1 5，看 r 列与 wa 列 4）iostat -x 1 5（装了 sysstat 才有），看 %util 与 await 5）mount | grep -E 'nfs|cifs'，有网络存储先怀疑它 修复步骤（需确认后执行）： 1）先定位到具体设备或挂载点再动手，方向没定之前不要调任何参数； 2）如果是 NFS/CIFS 服务端慢，去恢复存储侧，加 CPU 完全无用； 3）如果是 cgroup IO 限流，调整 io.max，注意这会改变同一层其他容器的 IO 份额； 4）不要靠调 vm 参数去压 load，指标好看了问题还在。

验证步骤79 字

load average 的 1/5/15 三个值同步下降；/proc/pressure/io 的 some avg10 回落；ps 里 D 状态进程数减少。

回滚65 字

调整 cgroup io.max 前先记录原值（cat /sys/fs/cgroup/.../io.max）；纯只读步骤无需回滚。

需确认40 字

这台机器有没有挂 NFS/CIFS、业务是否跑在容器里、块设备是本地盘还是云盘。

另外三项没画图，脚本里一起输出了：100 条问法不重复（0 条重复）、训练集与验证集 0 条串味、100 条 system 完全一致（True）。

规则

随机 1 到 100、提示大了小了、记次数、猜对给重开。这四条定死了，就没有「猜 0 到 999」这种自选动作。

边界

写清「只交一个能直接打开的 HTML 文件」，它就不会拆成 html + css + js 三个文件，也不用起服务才能看。

输出格式

「不要外部图片」这句省掉了找图、放图、图裂三轮；「字号大到手在手机上能看清」比「好看一点」可执行得多。
